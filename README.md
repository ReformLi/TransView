# 局域网媒体中心与传输工具（TV端 + 手机网页）需求文档

**版本**：v1.36  
**日期**：2026-09-18  
**状态**：核心功能已实现（v1.0.0 APK），本文档已同步实际实现  

> v1.36 变更：**媒体库「文件夹消失又瞬间出现」+ 切目录「一卡一卡」修复** —— 切换分类标签、以及按返回上一级时，文件夹会**肉眼可见地消失再瞬间出现**，整体感觉一卡一卡。根因是**两个数据源的速度差一个数量级**却拼进了同一个列表：**文件**来自 Room 的 `observeByType` 流（表已在内存），切目录**同一帧**就对；**文件夹**只能走**真实磁盘 IO**（`listChildren` + 对每个子文件夹的递归校验，DB 不索引文件夹），要晚若干帧、U 盘上可达数百毫秒。而拼装是 `dirEntries.filter { it.parentPath == currentDir } + fileEntries` —— 切目录那一帧 `dirEntries` 还装着**上一个目录**的列表，被新 `currentDir` **整批滤掉** ⇒ 首帧「0 个文件夹」，等扫描回来才整批出现。「返回上一级」**100% 命中**（它回到的目录刚看过却照样重扫）；「切换标签」更重 —— `when (selected)` 的三个分支是**不同调用点**，整棵子树被 dispose、全部 `remember` 重来，于是「转圈 → 只有文件 → 文件夹补上」**三层闪**叠加。修法两条：**A · 按目录缓存文件夹列表**（`DirListCache`，模块级而非 `remember` —— 缓存必须活过切标签；命中即**首帧即正确**，失效走**惰性**：条目记下扫描时的「代」，访问到旧代才重扫并**原地覆盖**，绝不全局清空）；**C · 消除数据源抖动**（两条 Room Flow **必须用 `remember` 固定实例** —— Room 每次调用都新建 Flow 对象，而 `collectAsState(initial)` 以**流对象本身**为 key，原来**每次重组都重建订阅、重跑查询**，这是「一卡一卡」的另一半；`childCountMap` 从组合期（主线程，`O(n·深度)`）移到 `produceState` + `Dispatchers.Default`）。另：**「未就绪」不再当成「空」渲染** —— 加载态判据合并为 `dbItems == null || !dirsReady || childCountMapOrNull == null`，顺带修掉根目录闪「暂无文件」提示的问题。（见 ARCHITECTURE §3.3.1 / §3.6 修法十）

> v1.35 变更：**返回键「一次按下被执行两遍」修复（真机电视）** —— 焦点在「上传」标签上按**一次**返回就**直接退出应用**（先弹「再按一次返回键退出应用」、随即兑现），以及文件夹里按**一次**返回**连跳两级**、越过本分类根目录看到沙盒总目录里的 `Pictures`（「图片总文件夹」本不该从图片页到达）。根因：真机遥控器的一次返回**可能投递两个抬起**（该遥控器事件序列与键盘不同 —— OK 键上已实测「按住只送一串重复 KeyDown + 最后一个 KeyUp」），而 v1.34 的补派发让每个抬起都变成一次完整的 Back 处理 ⇒「一次按下 = 两步操作」。修法三层：① **源头去重** —— 抬起**没有配对的按下**且距上次处理 ≤150ms（`BackKeySignal.DEDUP_MS`）⇒ 认定同一次物理按键，整条丢弃（W 级留痕，日志即证据）；② **退出确认加最小间隔** `EXIT_CONFIRM_MIN_MS` = 250ms —— 无论重复事件以何种形态漏过源头，都不可能「按一下就退出应用」；③ **`goUp()` 三重加固** —— 判据改**实时** `currentDir`（不再用组合期的 `atRoot`，同一帧内它是旧值）、父目录**越界钳回分类根目录**（`IStorage.parentNode` 只钳在**沙盒根**）、150ms 内重复调用直接忽略。（见 §3.4.2 / ARCHITECTURE §3.6「修法七 / 修法八 / 修法九」）

> v1.34 变更：**返回键「第一次按下完全无副作用」修复（真机电视）** —— 三个关联焦点异常（内容区按返回焦点消失、文件夹内要按两次才返回上级、按上键恒定落到「图片」）已定位并修复。根因**不是**判据写错，而是**系统 Back 派发链本身可能断裂**：旧语义下 `ACTION_DOWN` 必须走到 `Activity.onKeyDown` 才会 `event.startTracking()`，抬起时 `Activity.onKeyUp` 才凭 `event.isTracking() && !isCanceled` 调 `onBackPressed()` → `OnBackPressedDispatcher` → 应用注册的 `BackHandler`；**DOWN 一旦被吞**（触摸模式退出按键被框架消费 / 焦点树消费 / 窗口焦点切换重置 tracking），`isTracking()` 恒为 false、`onKeyUp` **静默丢弃**，整条链断掉、`BackHandler` 永不执行 —— 于是「第一次按返回完全没反应（连文件夹都不返回上级）、第二次才生效」（第一次按键让设备退出了触摸模式）。模拟器不产生这种切换，故只在真机暴露。修法两条：① `MainActivity.dispatchKeyEvent` **最小侵入补派发** —— 仅当抬起时 `!isTracking || isCanceled`（系统一定不会派发）才自行调一次 `onBackPressedDispatcher.onBackPressed()` 并消费该事件；`isTracking && !isCanceled` 时原样放行。两分支互斥 ⇒ **无双触发**。② 新增 `ui/common/BackKeySignal` + 主界面**焦点兜底复检**：按完返回键 200ms 后若「标签栏无焦点且内容区无焦点」或「焦点只停在隐形锚点上」，显式把焦点送回当前分类标签 —— 消除「↑ 恒定落到「图片」、← → ↓ 全无反应」（框架几何搜索兜底的特征：参考框横跨整宽贴底时，只有向上能命中「离框中心最近」的标签）。**每一次按返回都必定生效、焦点必定可见。**（见 §3.4.2 / ARCHITECTURE §3.6「修法五 / 修法六」）

> v1.30 变更：**权限配置与适配兼容性专项审查** —— 权限面本就干净（无相机/定位/通讯录/电话/录音/蓝牙/AD_ID），修掉 2 处实质问题；适配侧确认**无任何硬编码分辨率**，但发现一条会随系统升级爆发的高危项。
> **①【权限】通知权限声明了却从未申请**：`POST_NOTIFICATIONS` 早在清单里，但全工程没有运行时申请 —— Android 13+ 上通知被系统**静默丢弃**，而前台服务的常驻通知是用户了解「服务器运行中 / 已休眠 / 已暂停」的**唯一**途径。修法：新增 `util/NotificationPermission`，在**存储授权通过后**申请一次（存储是硬门槛，通知是可选增强，不抢第一个授权框），用 `SettingsStore.notifPermissionAsked` 标记保证只主动弹一次；回调刻意留空 —— 拒绝不影响服务器运行。
> **②【权限】删掉多余权限与死代码**：`NetUtils.wifiManager()` 全工程零调用（唯一引用是它自己的定义）→ 连同 `ACCESS_WIFI_STATE` 一起删除（该权限只服务 `getConnectionInfo()`，而新系统上无定位权限时 SSID 恒为空占位值）。另外 `ACCESS_NETWORK_STATE` 本工程也零使用，但 `media3-common` / `media3-exoplayer` 各自声明了它（已核对 manifest 合并报告），删本工程那行 **APK 里照样存在**，且 Coil 的 `RealNetworkObserver` 正依赖它 —— 故一并去掉重复声明（最终清单中该权限仍在，来源变为 media3）。
> **③【适配】高危：Android 16 在大屏忽略 `screenOrientation`**（官方行为变更：***最小宽度（smallestWidth）* ≥ 600dp 的屏幕忽略 screen orientation / aspect ratio / resizability 限制**；官方例外清单明确排除 *Displays smaller than sw600dp*、游戏与用户主动选择应用默认行为者）。三个 Activity 都锁了 `landscape`，此前永不触发，API 36 起**平板竖屏 / 桌面窄窗口**下**真的会变竖屏** —— 而顶部导航栏是不换行不滚动的 `Row`，非紧凑态整行约需 **950dp**，届时右侧「设置」标签与状态徽标会被**挤出屏幕**。（**手机 sw 360~450dp 与 1080p 电视 sw 540dp 均 < 600dp，落在官方例外清单内、不受影响** —— 判据是**最小宽度**而非屏幕宽度，960dp 是电视的宽度、540dp 才是它的最小宽度。）修法**双管齐下**：(a) 清单声明 `PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` 恢复兼容模式（**注意这是有保质期的安全网 —— API 37 会移除该 opt-out**；且官方明确 targetSdk ≥ 36 时它**并不锁定大屏方向**）；(b) 代码侧真正具备宽度自适应：新增 `TOP_BAR_FULL_WIDTH_DP = 960` + `rememberTopBarTight()`，宽度不足时收窄顶部栏（隐藏品牌标题、标签改紧凑样式、徽标只留圆点 → 整行降到约 400dp）；阈值刻意取**严格小于 1080p 电视常见宽度 960dp**，保证该类电视 / 盒子**逐像素不变**（代价：估算需求 ≈950dp，余量仅约 10dp，**待真机实测确认徽标无裁切**）。
> **④【适配】`MainActivity` 补 `configChanges`**：另两个 Activity 早已声明，主界面漏了 —— 方向锁失效后旋转 / 改窗口尺寸会**重建 Activity**，`showSettings` 等普通 `remember` 状态被丢掉（`selected` 有 `rememberSaveable` 所以能活）。现与另两个 Activity 对齐。
> **⑤【数据】备份规则排除数据库**：`backup_rules.xml` / `data_extraction_rules.xml` 是 Studio 空模板 ⇒ **全量备份**，会把 Room 库一起带走 —— 而 `media_items.filePath` 是**卷根绝对路径**，跨设备恢复后全部不可达（反倒变成「不可达索引」要用户手动清）。现排除 `database` / `file` / `external` 三个域，只保留 `sharedpref`（用户设置）；媒体库本就是磁盘索引，启动时由 `SyncManager` 重新对账补齐，排除无副作用。
> **经核实「不是问题」**：`ACCESS_NETWORK_STATE` 的删除对 APK 无影响（media3 带着）；FGS 三个权限与 `ServerService` 的版本分支严格对应（<29 无类型 / 29~33 `dataSync` / 34+ `specialUse`），**不要简化**；`MANAGE_EXTERNAL_STORAGE` 是核心功能的唯一可行解（工程硬约束「禁用 SAF / DocumentFile」），保留但需知悉 Google Play 对其有政策申报要求（侧载不受限）。（详见 ARCHITECTURE §3.27）

> v1.30 变更：**上传大文件 OOM 修复（手动流式 multipart 解析）** —— 修复真机上传 1.74GB `.mp4` 报 `java.io.IOException: Map failed` / `OutOfMemoryError`。根因：NanoHTTPD 2.3.1 的 `session.parseBody()` 内部用 `FileChannel.map()` 把**整个请求体**内存映射进虚拟内存，大文件在电视盒子上直接撑爆（曾见 §4.1「内存占用 ≤100MB」的旧指标，实为经不起大文件检验）。修法：**彻底重构 `TransHttpServer.receiveAndSave`，禁用 `parseBody()`**，新增私有 `MultipartStreamParser` 从套接字输入流按 boundary 手动流式解析——文件 part 用 **128KiB 缓冲边读边写**进 `Android/data/<包名>/files/upload_tmp/upload_*.tmp`（应用外部私有目录 + BufferedOutputStream），全程解析器堆占用 O(128KiB)，**与文件大小无关**。保留了进度计数（`CountingInputStream` 在网络接收层计数自动生效）、UTF-8 中文文件名解码（兼容 `filename=` / RFC5987 `filename*=`）、路径消毒、同名重命名、zip 自动解压等全部行为。接收整段 **try-catch-finally + `consumed` 标记**：成功才原子移入分类目录，失败 / 中断 / **哪怕是 `OutOfMemoryError`** 都在 finally 里物理删除临时文件（防残余）；NanoHTTPD 的 `TempFileManager` 体系（`parseBody` 专用）与迁移后无用的 `ExternalTempFileManager` 一并废弃，临时文件由解析器自建、`purgeOrphanUploadTemps()` 启动清扫兜底。（见 §3.2 / ARCHITECTURE §3.1、§3.23、§3.26.1）

> v1.29 变更：**「清不掉的数据 / 死文件 / 冗余代码」专项排查与清理** —— 逐类核实后修掉 5 处「前端无法清理」的实质问题，并删掉 1 份整死文件 + 4 处无用资源/代码。
> **① 上传临时文件永久残留（最严重，会吃 GB 级空间）**：NanoHTTPD 的临时文件靠 `TempFileManager.clear()` 在每次连接收尾删除，但**进程被杀 / 断电 / 系统回收**时它根本没机会跑 —— 半个上传就以 `upload_*.tmp` 永久留在 `Android/data/<包名>/files/upload_tmp/`。该目录**不在媒体沙盒内**（对账的 `.temp_unzip` 清理与媒体库都碰不到），**Android 11+ 用户连文件管理器都进不去**，此前**没有任何清理路径**。修法：新增 `TransHttpServer.purgeOrphanUploadTemps()`，在 **App 启动**（进程刚起 ⇒ 本进程不可能有在途上传，保护窗口取 0）与**服务器启动 / 设置页「清理缓存」**（保护窗口 10 分钟，避开「停服立刻重启」「清理时正在上传」两种竞态）三处清扫。
> **② 不可达索引前端无出口**：对账按「读不到 ≠ 被删」原则（防拔盘误删）**永不删除**「所属卷已不在设备上」的索引，媒体库又按活动沙盒过滤显示不到它们 —— 这些记录只能永远躺在库里。修法：设置页新增「**清理不可达索引**」：点开先统计条数（0 条直接提示），确认弹框写清风险，确认后连同级联的播放历史一并删除（判据是「连所属卷都不在卷列表里」，比「卷在位但已拔出」更严格，临时拔出的盘不在清理范围）。
> **③ 应用缓存无入口**：Coil 2.x 未显式配置 `diskCache` 时默认在 `cacheDir/image_cache` 建 LRU 磁盘缓存（已反编译 `SingletonDiskCache` 确认），它不在媒体沙盒里、「存储空间占用」统计不到、前端也没有清理入口。修法：设置页新增「**清理缓存**」（显示当前占用，确认后清理，并顺带清遗留上传残留）。**清理顺序很关键（v1.30 修正）**：必须**先**调 `Coil.imageLoader(context).diskCache?.clear()`（= `DiskLruCache.evictAll()`，会同步清内存记账 + 删条目 + 写 journal），**再**扫 `cacheDir` 其余子项并**跳过** `image_cache` 目录本身 —— 因为 Coil 的磁盘缓存是进程级单例、`DiskLruCache` 的 `initialized` 只执行一次、目录被外部删掉**不会重建**，直接删目录会打坏它的内存记账与 journal（后续写缓存抛 `FileNotFoundException`）。
> **④ 上传记录留了看不见的尾巴**：表保留 500 条、UI 只读 200 条 → 最多 300 条记录**查不到也删不掉单条**（只能全清）。修法：`MAX_RECORDS` 与 UI 上限对齐为 200（库里有多少条，上传页就能看到并逐条删多少条）。
> **⑤ 批量删索引撞 SQLite 参数上限**：Room 把 `filePath IN (:paths)` 展开成**等量**绑定参数，超过 999（旧版 SQLite 宿主参数上限）整条语句直接抛异常，被对账的兜底 `catch` 吞成「对账异常，已兜底结束」—— 表现是「一次删掉上千个文件后僵尸卡片永远清不掉且毫无提示」。修法：`MediaRepository.deleteByPaths` 分批（400/批）。
> **⑥ 冗余文件 / 代码**：删除整份死文件 `ui/common/VideoMeta.kt`（`object VideoMeta` 零引用，时长提取实际走 `FileUtils.extractVideoDuration`）；删除无引用的 `@color/ic_launcher_tint`；清掉 8 处未使用 import；清掉工程根目录的临时产物（`apk_info.tmp` / `tv_scroll_mem.py` / 空目录 `.tmp_test` / Gradle 残留 `.trash`），并在 `.gitignore` 补上 `*.tmp`、`.tmp_test/`、`.trash/`。

## 1. 产品概述

### 1.1 背景与目标

本项目旨在解决“手机离线视频/图片批量传到电视，并在电视上分类管理、续播观看”的需求。电视端 App 作为**接收端 + 媒体中心**，手机端**无需安装 App**，通过浏览器扫码即可上传文件。核心目标是：**传完即走、分类清晰、播放流畅、有历史记录**。

### 1.2 核心价值

* **零手机安装**：手机浏览器扫码即可上传，支持批量、文件夹与 zip 压缩包（自动解压、按分类过滤）。
* **自动分类**：视频、图片、其他文件分开管理，互不干扰。
* **媒体中心体验**：视频支持文件夹层级、播放历史、自动连播；图片支持全屏浏览。
* **智能保活**：默认智能模式按需启停服务器（省电不卡顿），可选极速模式 7×24 常驻；支持开机自启、端口与设备名自定义。

### 1.3 目标用户

* 拥有 Android TV / 电视盒子的用户。
* 手机中存有大量离线 MP4、图片等文件，希望搬到电视上观看。
* 不希望在手机和电视上安装复杂投屏 App，追求轻量、免费、无广告。

### 1.4 使用场景

1. 用户手机下载了一部电视剧（多个 MP4 文件），通过网页上传到电视的“视频”分类，电视端自动合并到同名文件夹，点击文件夹可查看剧集并续播。
2. 用户手机拍摄的照片，通过网页上传到“图片”分类，电视端全屏展示。
3. 用户上传 APK、PDF 等文件到“其他”分类，电视端调用系统工具打开。

## 2. 总体架构

### 2.1 系统组成

* **TV 端 App**：Android TV 应用，内嵌 HTTP 服务器、媒体库、播放器。
* **手机端**：任意浏览器（Chrome、Safari、微信内置等），访问 TV 端提供的网页上传界面。
* **网络要求**：手机与电视必须在**同一局域网**（同一 Wi-Fi 或网段）。

### 2.2 数据流

手机浏览器 → HTTP POST（multipart/form-data） → TV 端 HTTP 服务器 → 保存文件到本地目录 → 触发媒体库扫描 → 媒体中心展示 → 播放器播放。

## 3. 功能需求

### 3.1 TV 端界面与交互

**矮屏（手机横屏）适配（v1.18 / v1.19 / v1.20）**：屏幕高度 < 480dp 时全端自动切到紧凑形态 ——
顶部导航栏收紧留白与字号、隐藏品牌标题与状态文字（§3.1.1）；**内容区整体等比缩放**：
`CompactContentDensity` 覆盖 `LocalDensity`（density × 0.87），内容区里所有 dp / sp 同步缩小
（字号与间距 / 图标 / 卡片的比例关系不变），主体文字 16sp → 约 13.9sp，与紧凑顶部栏的
`labelLarge`(14sp) 视觉齐平；媒体库列数的屏宽收敛改用缩放后的**实际**宽度（避免把设置的「6 列」误压成 5 列；
列数仍以设置为上限，**不会**把 5 列自动变多）；**设置页左右两栏各自可滚动**（v1.20，见 §3.1.5）——
矮屏上「设置」分组列表与右侧详情都可能高于一屏，固定布局会把末项裁掉。
三处判据统一为常量 `COMPACT_SCREEN_HEIGHT_DP = 480`。
**TV / 平板不做任何缩放、内容不超出视口也无需滚动，逐像素与改造前一致**（详见 ARCHITECTURE §3.20 / §3.21）。

**顶部导航栏的宽度自适应（v1.30，独立于上面的高度判据）**：顶部栏是**不换行**的 `Row`，非紧凑态整行约需 **950dp**（品牌标题 + **4 个媒体标签** + 设置标签 + 状态徽标）。Android 16 起**最小宽度（smallestWidth）≥ 600dp** 的屏幕忽略 `screenOrientation`，平板竖屏 / 桌面窄窗口下这一行会被**挤出屏幕**（右侧「设置」标签与状态徽标丢失）；手机（sw 360~450dp）与 1080p 电视（sw 540dp）都 < 600dp，落在官方例外清单内、**不受影响**。故新增 `rememberTopBarTight()`：**高度 < 480dp（矮屏）** 或 **宽度 < `TOP_BAR_FULL_WIDTH_DP`(960dp)** 任一成立即收窄顶部栏（隐藏品牌标题、标签改紧凑字号与内边距、徽标只留指示圆点 → 整行降到约 400dp）。阈值刻意**严格小于 1080p 电视常见宽度 960dp**，故该类电视 / 盒子**逐像素不变**（代价：估算需求 ≈950dp 与阈值仅差约 10dp，**需真机实测**）；内容区缩放另由 `CompactContentDensity` 按高度判据独立负责，两者互不影响（平板竖屏时内容区仍按电视尺度排版，但顶部栏已收窄）。

#### 3.1.1 顶部导航栏

* 包含四个标签页：**上传**、**视频**、**图片**、**其他**；右侧偏右位置固定放置**「设置」**入口（与媒体标签以大间距分隔，位置不随标签切换移动）。
* 默认选中“上传”页。
* 遥控器左右方向键可切换标签，切换时下方内容区同步刷新（**聚焦即选中**）。
* 「设置」入口同样**聚焦即打开**：焦点落到「设置」时内容区立即切换为设置子页面（§3.1.5），焦点保持在「设置」上，按 ↓ 进入设置选项；设置页打开期间媒体标签不显示选中态，避免高亮误导；从「设置」按 ← 回到媒体标签时自动关闭设置页并切回对应媒体页。
* 焦点在内容区时，按“返回”键回到顶部导航栏。

#### 3.1.2 焦点控制

* 所有可点击元素必须有明确的焦点状态（高亮、放大等）。
* 使用 `nextFocusUp/Down/Left/Right` 或 Compose `FocusRequester` 保证遥控器操作流畅。
* 列表滚动时焦点自动跟随。
* **触摸 / 鼠标点按内容区后，焦点自动锚回内容区**：点按一次之后按方向键不会跳到顶部标签把页面切走，而是从本页第一个元素（记录首行 / 网格首项 / 设置首项）继续。遥控器按键路径不受影响。

#### 3.1.3 上传页（默认）

**布局为左右分栏**（按屏幕宽度占比自适应，非固定像素）：

* **左侧固定区**（宽屏约 31%、**矮屏紧凑模式 46%**，不滚动）：二维码 + 访问码 + 服务器地址 + 状态，随屏幕高度撑满。
  * 显示二维码，内容为 `http://[电视IP]:[端口]/?token=[访问码]`——扫码即自动通过认证，零输入。
  * 二维码下方是**访问码色块**：一条横铺面板、主色 14% 透明的圆角条，条内「访问码」小标签与 6 位码值同行居中（码值 `headlineSmall` + 字距 4sp）。做成色块而非裸文字，是为了让访问码从上下两条信息（二维码 / 地址）里独立出来，不至于像「小标签贴在大字左边」的错位行；供无法扫码、只能手输地址的手机照着屏幕输入（见 §3.2.6）。
  * 再下方显示纯文本 IP 和端口，方便手动输入；地址下提供「复制链接」按钮（遥控器点击复制**带访问码的完整链接**到剪贴板，粘到手机浏览器等同扫码；Toast 确认）。
  * 左上角标题用 `labelLarge`（不用 `titleMedium`）：面板竖向是一条「越往下越次要」的信息流，标题不该和访问码抢层级，也省出 4dp 高度。
  * 二维码尺寸**随可用空间自适应**（`BoxWithConstraints` 取正方形边长）：固定尺寸在 720p 电视上会把面板下方文案挤出可视区，自适应后小屏不溢出、大屏也不会被放大过头。面板竖向预算很紧（每一块都影响二维码能长多大），因此底部提示只留一行；实测 720p 下二维码占面板宽的 80%。
  * **矮屏（手机横屏）紧凑模式（v1.18）**：内容区高度 < 480dp 时（判据与顶部导航栏同一阈值）自动切换 —— 整页留白收紧（40/18 → 16/10）、左面板占比提到 46%、省略左上角标题、**地址与「复制」并排一行且复制只留图标**（省 36dp）；窄机型横屏仅约 640dp 宽时地址自动折成两行。目的只有一个：把竖向预算尽量还给二维码（从「被压到几十 dp」恢复到 ~145dp），并让地址不再被截成「…」。
  * 显示当前服务器运行状态（运行中/已暂停/已休眠/已停止）与当前保活模式。
  * 服务器未运行时，二维码位置显示状态面板：休眠显示「唤醒服务器」按钮（<1 秒恢复监听），省电模式显示「启动服务器」按钮，播放/熄屏暂停显示自动恢复提示。
* **右侧记录区**（约 70% 宽，可滚动）：数据库驱动的上传记录列表（六要素：文件名 / 大小 / 进度 / 状态 / 时间 / 分类）；表内自动只保留最近 500 条（列表最多显示 200 条，更早的属无人会读的历史日志，自动裁剪防无限增长），App 启动对账时把进程被杀残留的「上传中」僵尸记录统一标为失败。
* **上下键层级**：记录列表**第一行**按 ↑ → 列表头「清空所有记录」（本页工具条）→ 再 ↑ → 顶部导航栏「上传」标签；从「上传」标签按 ↓ 回到记录首行。
  这一层必须显式指定——记录区在屏幕右侧，其正上方就是导航栏右上角的「设置」，交给默认就近搜索会把焦点送进「设置」。
* **左右边界**：焦点在某条记录上按 → 焦点原地不动（记录行已撑满右侧宽度，不会「环绕」到顶部标签）。
* **删除后的焦点**：删掉一条记录后焦点自动落到**下一条**（删的是最后一条则退到上一条），不会回退到顶部「上传」标签（见 §3.6 的「焦点安全港」）。

#### 3.1.4 视频页 / 图片页 / 其他页

* 统一为**多列网格卡片**（`LazyVerticalGrid`，**不提供单列列表**），宽屏电视一屏尽量多展示。
* **列数由「设置 → 界面设置 → 网格列数」决定**（4 / 5 / 6，默认 5）。列数同时驱动网格的**行首/行尾焦点边界**判定，改动后返回媒体库即生效。
* **默认排序方式同样来自设置**（名称 A-Z / Z-A、时间新→旧 / 旧→新，默认名称 A-Z）：进入媒体库时按它开局，用工具条「排序」做的临时调整只作用于本次浏览，不写回设置。
* 卡片样式：
  * 文件夹卡片 = 文件夹图标 + 名称 + 「N 个文件」副标题；
  * 视频卡片 = 缩略图（首帧，16:9）+ 名称 + 「时长 · 大小」副标题，有播放记录的卡片底部叠加细进度条；
  * 图片卡片 = 缩略图 + 名称；
  * 其他卡片 = 通用类型图标 + 名称 + 大小。
* 顶部工具条：**路径面包屑**（如「视频 > 甄嬛传」）+「排序：xxx」按钮 +「刷新」（触发对账；对账期间文案变「对账中…」并置灰，但**仍保持可聚焦**——否则焦点会回退到顶部标签导致页面被切走）。
* 焦点：卡片聚焦放大 1.1 倍 + 2dp 主色高亮边框 + 抬升层级；从文件夹返回上级时焦点自动还原到刚才进入的那张文件夹卡片；焦点在卡片上按**确定键**直达动作（进入/播放/查看/打开）。
* **上下键层级**：网格**第一行**按 ↑ → 本页工具条（排序 / 刷新）→ 再 ↑ → 顶部导航栏里**本页分类对应的标签**（视频页 →「视频」，不再固定跳第一个「上传」）；中间行按 ↑ 仍是网格内上行；工具条按 ↓ 回网格。
* **左右边界**：焦点在每行最左 / 最右的卡片或工具条两端时，按 ← / → 焦点原地不动，不会「环绕」到顶部标签上去。
* 支持按名称、添加时间排序（工具条「排序」按钮或遥控器菜单键调出排序选项）。

* 左侧分组：上下键切换分组；按 **→** 进入右侧详情列表；首分组按 **↑** 回到顶部「设置」标签；末个分组按 **↓** 吃掉。
* 右侧详情：上下键在设置项间移动；按 **←** 回到左侧当前分组；每组首行按 **↑** 回到顶部「设置」标签；**每组末行按 ↓ 吃掉**（与左栏末项、关于组末条同规；漏掉会环绕到左栏「服务器与网络」）；行首按 ←、行尾按 → 的边界处理与媒体页一致（不环绕到顶部标签）。
* **触摸点按空白处 / 滑动**（v1.21）：触点没有落在任何可聚焦行上时（行间 6dp 间隙、行左右各 12dp 留白、不可聚焦的小字提示、卡片边缘），焦点**锚回最后聚焦的那一行 / 那个分组**，不再无条件跳回「服务器与网络」。
* 激活设置项（按**确定键**或**→**）→ 弹出单选列表 / 二次确认小弹框，选完自动关闭，**焦点必须回到刚才那一行**。
* **「关于」组不弹框**：内容直接内联在右侧详情区（应用信息 / 声明 / 开源许可 / 致谢名单），每条信息都是一个可聚焦条目（按确定或 → 都没有动作）；内容超出可视区时随焦点上下移动自动滚动。首条按 ↑ 回顶部「设置」标签，末条按 ↓ 吃掉按键（防止环绕到顶部标签切页）。
* 单选弹框**打开时焦点落在当前选中项**上（不是第一项）：否则高亮与「● 当前值」分处两行看着像两个选中项，且直接按确定会静默改成第一项。
* 返回键：先退出设置页（如弹框打开则先关弹框），回到主界面当前媒体页。

### 3.2 网页上传逻辑（手机端）

#### 3.2.1 页面结构

* 标题：显示“上传到电视”。
* 分类选择器：**视频**（默认）、**图片**、**其他**。
* 文件选择区域：支持点击选择文件、拖拽文件/文件夹到区域。
* 上传按钮。
* 上传进度列表：显示每个文件的名称、大小、进度条、状态（等待/上传中/成功/失败/已取消），每行带操作按钮——**排队中 / 上传中 → 取消**，**失败 / 已取消 → 重试**（重试沿用原文件，无需重选）。

#### 3.2.2 分类规则

* **视频**：仅允许视频格式（.mp4, .mkv, .avi, .mov, .flv, .wmv 等）。
  * 点击选择文件时，`accept` 属性限制为视频格式。
  * 拖拽上传时，若包含非视频文件，提示“格式有误，仅支持视频文件”，并忽略非视频文件。
* **图片**：仅允许图片格式（.jpg, .jpeg, .png, .gif, .bmp, .webp 等）。
  * 规则同上。
* **其他**：接受除视频和图片外的所有文件格式（.pdf, .apk, .zip, .txt 等）。
  * 不限制格式，但需提示“其他文件将调用电视系统工具打开”。

#### 3.2.3 上传方式

* **单/多文件上传**：点击选择，支持多选。
* **文件夹上传**：使用 `<input type="file" webkitdirectory>`，保留文件夹结构。
* **压缩包上传**：选择「视频 / 图片」分类时可直接选 `.zip`，电视端自动解压并只保留该分类的文件（固定行为，无开关）；选择「其他」分类时 `.zip` 原样保存，不解压。
* **拖拽上传**：支持将文件或文件夹拖拽到页面区域。

#### 3.2.4 上传进度

* 每个文件独立显示进度条（百分比）。
* 支持取消上传（可选）。
* 上传完成后显示“成功”或“失败”状态。

#### 3.2.5 格式过滤

* 文件夹上传或压缩包解压时，根据当前分类自动过滤：
  * 视频：只保留视频格式，删除其他格式。
  * 图片：只保留图片格式。
  * 其他：保留所有非视频、非图片格式。

#### 3.2.6 访问码认证（已实现，最小实现）

**目标**：在不破坏「扫码即传、零手机安装」的前提下加一道门槛，让同网段不知道访问码的设备无法上传。

访问码为 6 位随机码（字符集 `A-Z` + `0-9`），显示在电视「上传」页二维码下方；**会话内固定**——电视端 App 进程存活期间（含熄屏、播放暂停、休眠恢复、改端口）沿用同一码，重启电视端 App 才轮换。这样「边看视频边让家人传文件」不会被反复打回输入访问码界面，与主流投屏 / 传输工具「会话内记住配对」的惯例一致；旧码随进程死亡即失效，安全性不打折。

* **情况 A：扫码进入（`http://IP:端口/?token=XXXXXX`）** —— 二维码里已经带上访问码，网页解析 URL 后自动取用，**用户完全无感**，直接看到上传界面。
  * 取到后立即把访问码从地址栏抹掉（`history.replaceState`）：避免刷新/收藏/转发时带着一个可能已失效的码反复进入上传界面，也避免访问码随 URL 泄露给被转发到的其他设备。
* **情况 B：手动输入 IP 进入（URL 无访问码）** —— 不显示上传界面，而是显示**「输入访问码」界面**：提示语 + 输入框（`maxlength=6`，`oninput` 自动转大写并剔除非字母数字字符，回车即提交）+「确认」按钮 + 错误提示区。
  * 点「确认」先请求 `GET /verify?token=...` 预校验：返回 200 才放行，否则提示「访问码错误，请重试」。
  * 补充：URL 无访问码但**本标签页已验证过**（用户按了刷新）→ 复用 `sessionStorage`，不必重复输入；**新开标签页**（书签/直连）一律重新过门槛。
* **上传时携带**：所有 `POST /upload` 请求头带 `X-Upload-Token`。
* **认证失效处理**（电视端 App 重启后轮换了新码）：清掉本地访问码、**暂停上传队列**（否则剩余文件会被逐个撞成 403 全标失败）、自动回到「输入访问码」界面并提示「认证已失效，请重新输入电视屏幕上显示的访问码」；重新输入正确访问码后队列**自动续跑**。电视端进程内的停启（熄屏 / 播放 / 休眠恢复 / 改端口）不换码，已验证的手机页面不受影响。
  * 兼容浏览器行为差异：服务端在读完请求体之前就回 403 并关闭连接时，浏览器（大文件尤其明显）报的是**网络错误而不是 403**。故上传中断后会先探一次 `/verify`：403 → 判定为访问码失效；200 → 按真实「连接失败」提示；探针本身失败 → 维持原有「服务器可能已休眠」提示。

**不做**（最小实现范围）：访问码过期时间、主动刷新接口、多用户、权限分级、HTTPS、「记住访问码」。同一访问码可被多台手机同时使用，不做单设备绑定。

### 3.3 文件接收与存储（TV 端）

#### 3.3.1 HTTP 服务器

* 使用 **NanoHTTPD**，监听**设置项指定的端口**（默认 2333，可在设置页从预设 2333/5210/8080/8888/9527 中单选），运行在前台服务中，启停由智能保活策略（§3.6）统一调度。
* 根路径 `/` 返回上传网页（每次请求现读模板并注入当前设备名）；**根路径不校验访问码** —— 网页得先加载出来，才有地方显示「输入访问码」界面。
* 访问码校验接口 `GET /verify?token=xxxxxx`：匹配返回 200，缺失或不匹配返回 403（大小写不敏感）。
* 上传接口 `/upload` 接收 POST 请求，解析 `multipart/form-data`；**需带请求头 `X-Upload-Token`，缺失或不匹配直接 403**（`{"status":"error","message":"认证失败"}`），且**不接收任何文件**——校验放在函数最前面，此时既没建上传记录也没读请求体。详见 §3.2.6。
* **手动流式解析 multipart**（v1.30，禁用 `session.parseBody()` 的内存映射方案）：从输入流按 boundary 切分，文件 part 用 **128KiB 缓冲边读边写**进临时文件——全程堆占用 O(128KiB)，与文件大小无关，修复了旧实现 `FileChannel.map()` 对大文件撑爆虚拟内存的 `OutOfMemoryError / Map failed`。中文文件名按 UTF-8 解码（兼容 `filename=` / RFC5987 `filename*=`）。
* 支持大文件上传，不限制文件大小（受电视存储限制）；上传临时文件写入外部存储私有目录（与目标目录同卷，保存时零拷贝移动）；接收整段 **try-catch-finally**，失败/中断/OOM 物理删除临时文件（防残余），成功才原子移入分类目录。
* 文件名与相对路径服务端消毒：过滤 `../`、路径分隔符、控制字符，防路径穿越。
* 返回 JSON 响应：`{"status":"ok","filename":"xxx.mp4"}` 或 `{"status":"error","message":"..."}`。

#### 3.3.2 存储路径（v1.1 修正：专属沙盒目录）

* **专属沙盒根**：`/sdcard/TransView/`，内部固定三个子目录：
  * 视频：`/sdcard/TransView/Movies/`
  * 图片：`/sdcard/TransView/Pictures/`
  * 其他：`/sdcard/TransView/Downloads/`
* 手机上传的文件严格保存到上述对应目录；上传的文件夹在对应子目录下重建层级。
* **扫描范围限制**：SyncManager 对账只扫描 `/sdcard/TransView/`，绝不扫描系统公共目录（`/sdcard/Movies/` 等），避免误扫系统垃圾文件。
* **异常兜底（预期行为）**：用户用 U 盘往 `/sdcard/TransView/Movies/` 拷电影，启动/刷新对账会正常扫描入库并展示在媒体库（用户主动行为）。
* **清理/删除范围限制**：空文件夹清理与文件删除操作必须验证路径位于 `/sdcard/TransView/` 内（`FileLocations.isInsideSandbox` 规范化路径断言），防止越界误删系统文件。

#### 3.3.3 同名处理

* **文件同名**：若目标文件已存在，自动重命名，在文件名后加 `(1)`、`(2)` 等后缀，直到不重名。例：`视频.mp4` → `视频(1).mp4`。
* **文件夹同名**：若上传的文件夹与已有文件夹同名，**合并**到同一文件夹中，不覆盖已有文件，内部同名文件按上述规则重命名。

#### 3.3.4 文件夹上传解析

* 解析 `webkitRelativePath`，在服务端重建文件夹结构。
* 若目标目录已有同名文件夹，则合并内容。

#### 3.3.5 压缩包解压（已实现）

触发条件是**分类 + 后缀**两者同时成立（固定行为，无设置开关）：当前分类为视频/图片、文件后缀为 `.zip`
即自动解压——**分类本身就是意图表达**，想把 zip 原样保存就选「其他」分类。任一条件不满足，`.zip` 就按普通文件落进所选分类目录。

流程（服务端 `ZipExtractor`，全程 `Dispatchers.IO`，不阻塞 UI）：

1. **暂存**：上传的临时文件移入工作区 `/sdcard/TransView/.temp_unzip/u<时间戳>/archive/`（保持用户原始文件名）；
2. **元数据预估**：读 ZIP 中央目录，只统计匹配当前分类的条目，累加未压缩大小得到预估体积；
3. **空间校验**：剩余空间 < 预估体积 × 1.2 → 拒绝解压，提示「存储空间不足，已保留原压缩包」；
4. **流式解压**：解压匹配条目到工作区 `files/`，**保持压缩包内的目录结构**；非本分类条目直接跳过不落盘。
   固定 64KiB 缓冲区，内存占用与文件大小无关；累计写入超过可用空间立即中止（防伪造元数据的膨胀包）；
5. **归位**：命中文件经 `UploadStorage.save` 搬进分类目录（同名自动 `(1)(2)` 后缀、不覆盖；同名文件夹合并），
   并立即写入媒体索引；
6. **收尾**：删除工作区；解压成功即删除原包（解压出的文件与原包内容重复，删包避免双份占空间）。

安全与兜底：

* **Zip Slip 防护**：条目名经 `sanitizeRelativePath` 清洗（剔除 `..`、绝对路径、隐藏段、盘符），
  落点再做一次 `canonicalPath` 前缀校验，越界条目直接丢弃（实测：`abs.zip` / `deep.zip` 未在沙盒外产生任何文件）；
* **失败必保留原包**：一个目标文件都没找到 / 空间不足 / ZIP 损坏 / 归位失败 → 原包一律移入 `Downloads`
  并提示（如「压缩包中未找到视频文件，已保留原压缩包」）——失败路径与「成功删包」是两回事，任何失败都不丢用户文件；
* **中文包名兼容**：Windows 资源管理器压缩的包用 GBK 编码条目名且不置 UTF-8 标志位，
  优先按 UTF-8 打开、发现替换字符或异常时改用 GBK 重开（否则整包解不出来）；
* **残留清理**：工作区目录名以 `.` 开头，媒体扫描天然跳过；`SyncManager` 每次对账（App 启动 / 手动触发对账）
  第一步就物理清空 `.temp_unzip` 下的残留，防止解压途中断电留下半个工作目录。

#### 3.3.7 U 盘接入：直接文件路径扫描 + 写探针（v1.14）

**要解决的问题**：v1.12 / v1.13 为「U 盘挂载点对 App 不可见」引入了 SAF（`ACTION_OPEN_DOCUMENT_TREE`
授权 + 文档树读写），并为此补了一整套兼容性兜底（六道防护 + 手动指定路径）。但**真机（Vidda 电视）实测**：
系统把 SAF 的目录选择器彻底屏蔽，**授权根本不可能成功**；而用第三方文件管理器验证，U 盘的物理路径
`/storage/0000-0000` **实际可读可写**。结论是——问题不在权限，而在「系统不上报存储卷」。
于是 v1.14 **彻底移除 SAF**，回到纯 `java.io.File`。

**做法一：多来源枚举候选卷根 + 写探针**（`FileLocations.getWritableDevices()`）

> ⚠️ **踩过的坑（API 36 实测）**：一开始设计的「直接扫 `/storage/` 子目录」**行不通**——
> Android 11+ 起第三方应用（即便已获 `MANAGE_EXTERNAL_STORAGE`）**读不到 `/storage` 的目录项**，
> `File("/storage").listFiles()` 恒返回 `null`（日志实录：`扫描 /storage：-1 项 [读取失败]`）。
> 但**已知路径照样可读写**——Vidda 上第三方文件管理器能读写 `/storage/0000-0000` 正是这个道理。
> 所以策略改为「**先枚举候选卷根，再逐个写探针**」。

候选来源**四路合并、路径去重**（任一路失败不影响其它）：

* **①** `StorageManager.storageVolumes` 的 `getDirectory()`（API 30+；**电视 ROM 常返回 null**）；
* **②** 由卷 `uuid` 拼出的 `/storage/<uuid>` 与 `/mnt/media_rw/<uuid>`——`getDirectory()` 为 null 时的兜底，
  Vidda 正是「不上报目录、但路径可读写」这种情况；
* **③** `Context.getExternalFilesDirs(null)` 去掉 `/Android/data/<pkg>/files` 后缀反推卷根
  （**不需要任何权限**，且能发现系统承认的每一块可移动卷——**最稳的一路**）；
* **④** `/proc/mounts`（退化读 `/proc/self/mounts`）里 `/mnt/media_rw/<id>`、`/storage/<id>` 挂载点
  ——挂载表是 ROM 唯一藏不掉的证据。

然后：

* 对每个候选做**写探针**（`probeWritable()`）：在卷根建 `.transview_write_test` 再立即删除，
  **成功才认作可用设备**。这是唯一可靠的判据——`File.canWrite()` 在部分 ROM 上对可移动卷**恒返回 false**
  （传统 `WRITE_EXTERNAL_STORAGE` 不覆盖可移动卷根）而实际能写；反过来「`listFiles()` 非空」也不能证明可写。
  探针会在卷根留下一瞬的文件（建后即删），属沙盒外的一次性例外；
* 盘名优先取 `StorageManager` 的卷描述（按卷 UUID 匹配，**纯展示用**），
  取不到就显示 `U盘 (卷ID)`（如 `U盘 (0000-0000)`）；
* **内部存储恒为第一项**（`/storage/emulated/0`）；
* 前置条件：`MANAGE_EXTERNAL_STORAGE`（首启已引导开启「允许管理所有文件」）——直写可移动卷的必要条件。

**做法二：单实现存储抽象**（`IStorage` / `FileStorage`）

* v1.14 起 `SafStorage` 已删除，`IStorage` 只有 **`FileStorage` 一个实现**；`StorageFile.path`
  **恒为绝对路径**（如 `/storage/0000-0000/TransView/Movies/a.mp4`），它同时就是数据库
  `media_items.filePath` / `parentFolder` 的取值——UI 导航、对账比对、播放器取源用同一个字符串，天然对齐。
* 沙盒结构不变：`<存储卷>/TransView/{Movies,Pictures,Downloads}`，`isInsideSandbox` 越界断言照旧护住
  全部破坏性操作。
* **上传落盘直接 `FileOutputStream`**，不再需要 `ContentResolver` / `openOutputStream`；
  归位走 `FileStorage.moveFileInto()`——**同卷 `renameTo` 零拷贝**，跨卷（解压工作区 → U 盘）退化为
  `copyTo` + `delete`。
* **播放 / 看图 / 缩略图一律传 `file:///storage/…`**：ExoPlayer 的 `DefaultDataSource` 与 Coil 都原生支持，
  且**不走 IPC**，性能与稳定性都优于 `content://`（`MediaMetadataRetriever` 也改用 `setDataSource(path)` 版本，
  比 URI 版本更快）。

**做法三：设备列表即用户选择**（设置 →「存储与数据」→ **存储位置**）

* 弹框**直接列出自动扫描出的全部可写设备**，描述行带容量：
  `内部存储 → 可用：2.35GB / 共：3.71GB`；`U盘 (0000-0000) → 可用：14.5GB / 共：16.0GB`；
* 选中即把**卷根绝对路径**写入 `SettingsStore.preferredStoragePath`（同时记 `preferredStorageLabel` 盘名），
  随后 `FileLocations.refresh()` + 对账一次；弹框关闭、焦点回到「存储位置」那一行；
* **「首选但当前不在位」的盘**会以 `盘名（已断开）` 出现在列表里且**不可选**——这是「降级模式」在设置页里的
  可视证据，让用户看明白「我选的盘为什么不见了」；
* 不再有「添加 U 盘（需授权）」与「手动指定 U 盘路径」两行（见 §3.3.8）。

**降级与恢复（与前版完全一致）**：首选卷写探针失败 / 已拔出 → 自动降级为内部存储并 Toast 提示
（**上传不中断**），插回自动恢复。降级期间媒体库只展示当前活动存储的内容，**另一块存储的索引记录全部保留**，
切回即恢复。防误删不变式照旧：`existsForPath()` 对「所属卷当前不可见」的路径**一律判为存在**，
绝不删索引（「读不到」≠「被删了」）。

**触发点**：App 启动（`TransViewApp`）、外接盘插拔广播（`ServerService` 转发，去抖）、设置页切换首选存储、
每次对账开始前（`SyncManager`）。

#### 3.3.8 SAF 授权入口与「手动指定路径」的移除（v1.14）

v1.12 的「添加 U 盘（需授权）」与 v1.13 的「手动指定 U 盘路径」两个入口**已全部移除**，相关代码一并删除。

* **移除原因**：Vidda 等电视 ROM 实测 `ACTION_OPEN_DOCUMENT_TREE` 被系统屏蔽——v1.13 的六道防护能让
  App **不闪退**，但**授权本身仍不可能成功**；而 U 盘物理路径 `/storage/0000-0000` 实际可读写。
  既然 v1.14 改为自己扫 `/storage/`（见 §3.3.7），这两个兜底入口就都失去了意义。
* **依赖清理**：删除 `androidx.documentfile` 依赖（`build.gradle.kts` + `libs.versions.toml`）、
  `SafStorage` 实现文件、全部 `DocumentsContract` / `DocumentFile` 引用；设置页 20 余个 SAF 相关 import
  一并清掉（`ActivityResultContract` / `rememberLauncherForActivityResult` / `BasicTextField` /
  `KeyboardOptions` 等）。
* **设置键清理**：`SettingsStore.init()` 一次性删除历史键 `saf_tree_uri` / `saf_tree_label` /
  `manual_storage_path`；`preferredStoragePath` 读到**非 `/` 开头**的值（旧的 `content://` 文档树 URI）
  一律回落内部存储并**就地改写**该偏好，避免首选存储永久停在降级态。
* **历史索引清理**：`SyncManager` 对账新增步骤 **1.5**——把 `media_items` 里 `filePath` 以
  `content://` 开头的记录**全部删除**（这类记录指向的文档树已永久不可达，
  `existsForPath` 对 `content://` 恒返回 false，留着只会让媒体库出现点不开的僵尸卡片）。
  **与降级无关**：任何状态下都清，所以放在降级判断**之前**执行。
* **不变的部分**：`IStorage` 接口、`StorageVolume` / `StorageState` / `StorageEvent` 三件套、
  降级与恢复、防误删不变式全部保留，只是实现层从「双实现」收敛成「单实现」。

#### 3.3.9 崩溃日志落盘（v1.13）

电视上没有终端、拿不到 logcat，「白框一闪就退出」这类问题原来只能靠猜。v1.13 起
`CrashLogger` 接管**未捕获异常**：把时间 / 线程 / 版本 / 设备 / 异常与完整堆栈（含 `Caused by`）
追加写入 **`TransView/Downloads/crash_log.txt`**（与「其他」分类同目录 → 重启对账后可在 App 内打开，
也能拷到电脑看；与「App 调试日志」同一套路）。

* **绝不吞异常**：写完仍然调用原处理器，Logcat / 系统崩溃上报行为不变。
* **绝不二次崩溃**：全部 IO 包 `runCatching`，且**不触碰** `FileLocations` / Room 等可能正是崩溃源头
  或依赖初始化顺序的东西，落点直接用 `Environment` 拼内部存储沙盒（崩溃可能正因为那块 U 盘，往它上面写
  日志大概率失败）。
* **不无限增长**：超过 128KB 轮转为 `crash_log.old.txt`（只保留上一份，新崩溃覆盖旧备份）。

#### 3.3.10 App 运行日志本地化（「App 调试日志」开关，v1.17）

**背景**：`CrashLogger` 只兜「崩溃」这一个场景，而电视端**没有终端、拿不到 logcat** ——
对账异常、服务器起停、上传中断、存储降级这些**非崩溃**问题同样无据可查。
v1.11 那个「导出存储诊断日志」（已随 v1.17 一并移除、实现文件删除）是**手动、一次性、只针对存储**的，覆盖面太窄。

**做法**：新增 `util/AppLogger.kt`（单例），把运行日志**常态化异步落盘**，用一个设置项开关控制。

* **设置项（两级开关，均默认关）**：
  - **App 调试日志**（存储与数据 → `focusKey = "存储与数据:3"`）：**总闸**，值存 `SettingsStore.appLogEnabled`；
    切换后**立即生效**（无需重启）：开 → 建目录 + 起消费协程；关 → 停消费协程、关闭文件流、清空内存队列。
    副标题：「记录调试日志（仅供排查问题，长期开启可能影响性能）」。
  - **详细日志**（`focusKey = "存储与数据:9"`，**v1.31 新增**）：**二级开关**，值存 `SettingsStore.detailedLogEnabled`。
    与总闸**正交**（只在总闸开时有意义），开启后**额外**落盘 `V` 级。切换只翻转标志、不重启引擎，立即生效。
    副标题：「额外记录操作轨迹等细节；日志量较大，建议仅在排查时开启」。
* **三档等级 / 两级开关的语义**（v1.31）：总闸关闭时代价为零；总闸开启后 `W/I/E/D` 恒落盘（状态跃迁 + 全部失败），
  `V` 仅详细模式落盘（UI 操作轨迹、逐次存储探测、逐文件索引等**可高频**的诊断细节）。
  **硬约束：高频路径一律用 `V`，且禁止记「每字节 / 每毫秒」级事件**（如套接字输入流 `read()`、上传进度轮询）——
  队列满即静默丢弃，高频打点不会阻塞业务，但会把队列打满并挤掉真正有用的日志。
* **落盘结构**（根目录 = **当前活动存储**的沙盒，即 U 盘模式下天然落在 U 盘上）：

  ```
  <活动沙盒>/TransView/Downloads/app_log/
      └── 2026-09-16/              ← 按天分目录（yyyy-MM-dd）
              ├── 14-30-05.log     ← 会话首个文件，文件名即启动时刻（HH-mm-ss）
              ├── 14-30-05_1.log   ← 单文件写满 2MB 后按序号切割
              └── 14-30-05_2.log
  ```

  因为位于 `Downloads/` 下，`app_log/` 会被**严格按方案 A**（§3.4.x 目录即分类）当作**「其他」分类**
  扫描入库（`.log` 既非视频也非图片 → `mediaType=OTHER`），于是 **TV 端「其他」页能直接点开查看**。
  设置页开关下方有一行不可聚焦的小字提示，写明当前日志位置（内部存储 / U 盘）与查看路径。
* **防卡顿（核心）**：**绝不在调用点写磁盘**。`AppLogger.v/d/i/w/e` 只做两件事 ——
  ① 调一次原生 `android.util.Log`（**logcat 输出与改造前完全一致**，开发期照旧 `adb logcat`）；
  ② 把整行文本 `trySend` 进 `Channel`（容量 4096）后立刻返回；**队列满就丢弃该行，绝不阻塞业务线程**。
  真正的写盘在专用 `CoroutineScope(Dispatchers.IO)` 里：`BufferedWriter` 缓冲，
  **凑满 4KB 或空闲满 1 秒才 flush**（空闲时轻量轮询，不做任何 IO），严禁每条日志都 flush。
* **切割与清理（两道闸）**：单文件上限 **2MB**，写满立即关流、同日目录下按 `_1`/`_2` 递增新建
  （绝不允许单文件无限追加）；引擎启动时按顺序过两道闸：① **天数** —— 只保留最近 **7 天**的日期目录；
  ② **总量配额**（v1.31 新增）—— `app_log/` 总量上限 **50MB**，超出则从**最旧**的日期目录开始删，
  **至少保留 1 天**（超配额宁可略微超出，也不能清到一条不剩）。两道闸都有**双重保险**：
  目录名必须严格匹配 `yyyy-MM-dd`，且必须通过 `FileLocations.isInsideSandbox` 断言 ——
  只删 `app_log/` 下的旧日期目录，**绝不影响 Downloads 下的其他文件**。
* **兜底与边界**：所有内部操作 `runCatching` 包裹 —— 磁盘满 / 权限不足 / IO 异常一律**静默丢弃日志**，
  异常绝不冒泡到业务代码（**日志绝不能把 App 搞崩**）。
  **U 盘拔出**时写失败 → 关流清缓存 + 下一行重新解析落点，并（限流 30 秒）触发一次
  `FileLocations.refresh()`，活动存储自动降级为内部存储 → 日志无缝续写到内部沙盒，
  **绝不因为拔 U 盘而中断或崩溃**。写盘强制 `Charsets.UTF_8`，中文日志不乱码。
* **v1.31 全链路埋点**：调用点从 v1.17 的 **8 处 / 4 文件**（仅把原有 `Log.*` 换名）扩展到
  **约 90 处 / 20 文件**，覆盖服务器（`TransHttpServer` / `ServerController` / `ZipExtractor` / `UploadStorage`）、
  数据层（`SyncManager` / `MediaRepository`）、存储（`FileStorage` / `FileUtils` / `FileLocations`）、
  UI（`MainScreen` / `LibraryScreen` / `UploadScreen` / `SettingsScreen` / `ImageViewerActivity`）、
  播放器全链路与启动（`PlayerActivity` / `MainActivity` / `TransViewApp` / `BootReceiver` / `ServerService`）。
  **`CrashLogger` 刻意不接入** —— 它跑在「未捕获异常」路径上，硬约束是不触碰 `FileLocations`/Room
  （那可能正是崩溃源头），必须继续直接用原生 `android.util.Log`；同理 `AppLogger` 自身的内部失败
  也只走原生 Log，不进队。
* **静默丢弃而不是回压**：这是**故意**的设计取舍 —— 日志的价值远低于业务可用性，
  宁可丢日志也不能让上传/对账/播放因为写日志而变慢。

### 3.4 媒体库展示与管理

#### 3.4.1 分类展示

* **视频页**：展示所有视频文件和文件夹。支持文件夹层级，点击文件夹进入下一级。
* **图片页**：展示所有图片文件和文件夹。
* **其他页**：展示除视频和图片外的所有文件。

#### 3.4.2 网格视图（唯一形态）

* TV 端统一采用**多列网格卡片**（`LazyVerticalGrid`，列数 5），**不再提供列表视图切换**。
* 卡片展示：缩略图（图片 / 视频首帧）+ 文件名 + 副标题（文件夹=文件数；视频=时长·大小；其他=大小）；文件名与副标题**居中**对齐；「返回上级」卡片同样居中。
* 文件名过长时：未聚焦按省略号截断；**卡片获得焦点后标题循环滚动**（跑马灯），可完整看清名称；短名不滚动。
* 已观看过的视频卡片底部叠加一条细进度条，直观反映观看进度。
* 网格内按返回键先「返回上一级」，到分类根目录再按返回键才回到顶部导航栏。
* **返回键保证「一次生效、焦点可见」**（v1.34）：系统原有的 Back 派发链依赖 `ACTION_DOWN` 走到
  `Activity.onKeyDown`（`startTracking()` → 抬起时凭 `isTracking()` 才调 `onBackPressed()`），
  DOWN 一旦被吞（触摸模式退出 / 焦点树消费 / 窗口焦点切换）整条链就断，表现为「**第一次按完全没反应、
  第二次才生效**」且焦点消失；现由 `MainActivity.dispatchKeyEvent` 在「系统一定不会派发」时补派发一次
  （互斥分支，无双触发），并在按完后复检「焦点是否有人持有且看得见」，没有就显式送回当前标签 ——
  详见 ARCHITECTURE §3.6 的「修法五 / 修法六」。

#### 3.4.3 排序

* 支持按名称（A-Z / Z-A）、添加时间（新→旧 / 旧→新）排序。
* 排序选项通过遥控器菜单键调出。

#### 3.4.4 扫描触发

* 文件上传保存成功后，立即触发 `MediaScannerConnection.scanFile`，同时 TV 端媒体库列表**自动刷新**（无需切页或手动操作）。
* 也支持手动刷新（遥控器菜单键“刷新媒体库”）。
* 同一视频按文件名**自然排序**（EP2 < EP10）参与自动连播与列表展示。

#### 3.4.5 文件操作菜单（v1.4，菜单键 / 长按确定等效）

视频、图片、其他页的文件夹与文件卡片，弹出操作菜单（进入/播放/查看/打开、删除、取消）有**两个等效入口**：

* **菜单键**（`Key.Menu`）：按下即弹。
* **长按确定键**：按住 ≥ 系统长按阈值（约 400ms）后**松开瞬间**弹出；短按（< 阈值）仍直达动作（进入 / 播放 / 查看 / 系统打开）。触摸长按同效。
* 删除键：直接弹二次确认（与菜单内「删除」等效）。

**键盘 / 模拟器适配（实现要求）**：键盘按住 Enter（或空格、小键盘 Enter）时，输入通路会把 auto-repeat 拆成一串独立的「按下 + 抬起」事件对，事件自带的按压时长恒为 ≈0ms，且每次抬起都会触发一次点击（表现为「长按变多次确定」）。因此**不得信任事件时间戳**：按下事件全部拦截并自行用 `uptimeMillis` 记录起点；抬起时按压 ≥ 阈值 → 弹菜单，短按则延迟约 200ms 确认（窗口内无后续按下 = 用户真松手）才触发打开。「返回上级」卡片同样处理（防止按住连跳多级目录）。

### 3.5 播放与查看

#### 3.5.1 视频播放

* 使用 **ExoPlayer (Media3)** 播放。
* 支持格式：MP4、MKV、AVI、MOV 等常见格式。
* 支持字幕（外挂 .srt、.ass、.ssa、.vtt）、音轨切换、倍速播放（0.5x–2.0x）。
* 播放时自动记录进度到数据库（Room），每 2 秒及退出时入库。
* 再次打开同一视频时，弹出提示“是否从上次位置继续播放？”（进度 >10s 且未看完时）。
* **控制栏为「时间轴优先」结构**（v1.10，对齐 Netflix / tvOS 习惯），自上而下三段：
  * **内联选择器**：倍速 / 画面比例的横排胶囊（替代旧模态弹框）。非默认值时按钮直接显示当前值（如 `1.5x`、`拉伸`）；OK 打开、焦点落在当前选中项，再 OK 即选即生效并收起，Back / 上键收起且焦点回到来源按钮。
  * **时间轴（控制栏主角）**：进度条可聚焦，聚焦时轨道加粗 + 主色光环，一眼可辨「可拖动」；左右 = 拖动（与控制栏隐藏时同一套固定 10 秒步长 + 变速扫描）、OK = 播放/暂停。
  * **按钮行**：上一集 / 快退 / 播放暂停 / 快进 / 下一集 ｜ 倍速 / 比例 / 设置（⚙ = 音轨与字幕）。播放/暂停图标按「动作式」语义显示：**图标表示按下后会发生什么**——播放中显示「暂停」图标、暂停时显示「播放」图标。
* **音轨 / 字幕走右侧设置面板**：⚙ 按钮唤出右侧滑入面板（音轨、字幕两分区，轨道多时可滚动），OK 选择即生效并收起，Back 收起不改动；无对应轨道时显示占位提示。
* **快进/快退反馈为预览卡**（中央）：缩略图（异步取帧，`MediaMetadataRetriever` + 10 秒分桶缓存）+ 方向图标 +「`目标位置 / 总时长`」（如 `01:21 / 13:01`）——用户能看到将要跳到的那一帧，拖动不再是盲跳。短按一次固定 ±10 秒，按住 400ms 进入变速扫描（2x→4x→8x→16x；扫描期间不追帧，落点才取帧）。控制栏隐藏时连续快进只弹预览卡、不弹控制栏，不打断操作。
* **播完自动连播前先弹「下一集预告卡」**（右下、控制栏上方）：下一集缩略图 + 标题 +「N 秒后自动播放」倒计时（5 秒），焦点落在「立即播放」；倒计时归零自动切集，也可立即播放或取消（取消后停在片尾，徽标「已取消自动连播」）。最后一集播完停在片尾并弹出控制栏，由用户选择「重播」或返回，不自动退出（避免被误认为闪退）。
* 暂停后屏幕中央常驻「播放」图标（无背景遮罩），恢复播放即淡出，方便确认当前处于暂停态。
* 遥控器适配（时间轴优先按键模型）：
  * 中键：控制栏隐藏时播放/暂停；控制栏显示时交给当前聚焦元素（时间轴聚焦 = 播放/暂停，按钮聚焦 = 按下按钮）；
  * 左右方向键（控制栏隐藏时）：快退/快进（弹预览卡）；控制栏显示时是**焦点导航**（时间轴聚焦时为拖动），且会刷新 6 秒自动隐藏计时，不会出现「操作到一半控制栏消失、左右键突然变成快进」；
  * 上 / 下键：控制栏隐藏时唤出控制栏且**焦点落在时间轴**；显示时在「时间轴 ↔ 按钮行」间换轨，**最外缘再按同向收起**（时间轴上再按上 / 按钮行上再按下）；
  * 遥控器 ⏪ / ⏩ 媒体键：快退/快进（不受控制栏状态影响）；
  * ⏯ / ⏭ / ⏮ 媒体键：播放暂停 / 下一集 / 上一集；控制栏里的「上一集 / 下一集」在当前是第一集/最后一集时置灰，但**仍可聚焦**（灰色描边表示焦点、按确定键无效果），不会因为按钮突然不可聚焦而丢掉焦点；
  * 菜单键：显示或收起控制栏（6 秒无操作自动隐藏；选择器 / 设置面板 / 预告卡在场期间不自动隐藏）；
  * 返回键分层：预告卡 → 设置面板 → 内联选择器 → 控制栏 → 退出播放。

#### 3.5.2 图片查看

* 全屏展示图片，支持缩放（遥控器 +/- 或菜单键）。
* 支持遥控器左右键切换同目录下的上一张/下一张图片。
* 仅做展示，不提供编辑、裁剪、旋转保存等功能。
* 按返回键退出查看。

#### 3.5.3 其他文件打开

* 调用系统 Intent 打开：
  * APK → 系统安装器。
  * PDF → 系统 PDF 阅读器（如有）。
  * 文本 → 系统文本编辑器（如有）。
* 若系统无对应应用，弹出提示“无法打开此文件类型，请安装对应应用”。
* 不内置其他文件的专用查看器。

### 3.6 后台服务与智能保活（v1.1 更新）

#### 3.6.1 前台服务

* HTTP 服务器必须运行在 **前台服务（Foreground Service）** 中。
* **前台服务类型**：API 34+ 声明并使用 `specialUse`（`PROPERTY_SPECIAL_USE_FGS_SUBTYPE = lan_http_file_server`），API 29~33 回退 `dataSync`。原因有两条：① Android 15（API 35）起禁止 `dataSync` 类型前台服务从 `BOOT_COMPLETED` 启动（抛 `ForegroundServiceStartNotAllowedException`），而 `specialUse` 不在受限清单内；② `dataSync` 在 Android 15 上有 6 小时/天的时长上限，不适合 7×24 常驻的局域网服务器。
* 通知栏显示常驻通知，文案随服务器状态联动：**运行中 / 已暂停 / 已休眠 / 已停止**，点击回到 App。
* 服务进程内由 `ServerController` 状态机统一决策服务器启停；所有隐式 Intent（授权页、外部打开）经显式解析启动，规避部分 ROM 的 Instrumentation hook 问题。

#### 3.6.2 服务器智能保活策略

**信号源**：屏幕开关（SCREEN_OFF/ON 广播）、播放状态（ExoPlayer 播放中/暂停）、上传页可见性、上传活动（每次请求重置空闲计时）、手动唤醒按钮。

三种模式（设置入口：主界面顶部「设置」子页面 →「服务器与网络」→「保活策略」，v1.4 起为独立设置页；SharedPreferences 持久化，修改立即生效）：

| 模式           | 运行条件               | 说明                            |
| ------------ | ------------------ | ----------------------------- |
| 极速模式         | 恒运行                | 待机、播放、超时均不停止；需要"待机也能传"的旧行为选此项 |
| **智能模式（默认）** | 未休眠 && 屏幕亮 && 非播放中 | 待机/播放自动暂停（自动恢复，**在途上传传完才停**）；15 分钟无上传自动休眠 |
| 省电模式         | 在上传页 && 手动启动       | 离开上传页即停止（在途上传传完才停）              |

* **传输不中断（统一规则）**：任何原因的停服（熄屏 / 播放 / 离开上传页 / 空闲休眠）遇到在途上传都顺延，**传完最后一个文件才停**——「绝不中断传输」的承诺覆盖全部停服路径，与主流传输工具行为一致。
* **屏幕休眠联动**：熄屏自动暂停服务器极致省电，亮屏自动恢复监听（在途上传不受影响，传完才停）。
* **播放联动（重要）**：视频进入播放状态即暂停服务器，防止低性能设备（1GB 内存老盒子）"边播边传"卡顿；在途上传传完才停，暂停播放或退出播放器自动恢复。
* **无活动自动休眠**：上传结束后启动 15 分钟空闲计时；超时无新请求自动休眠，上传页显示「唤醒服务器」按钮，点击 <1 秒恢复。仍有上传在途（单个大文件传输超时）时顺延计时。
* **手机端联动提示**：网页连接失败时提示"电视端服务器可能已休眠或正在播放视频，请唤醒/等待恢复后重试"。

#### 3.6.3 开机自启

* 监听 `BOOT_COMPLETED` 广播（`RECEIVE_BOOT_COMPLETED` 权限），用户可在设置中开启/关闭；开启时自动启动前台服务，是否真正监听仍由保活策略决定。
* 应用首次安装后需先手动打开过一次，否则处于 stopped 状态收不到该广播（Android 3.1+ 系统限制）。
* 前台服务类型见 §3.6.1：API 34+ 用 `specialUse`，因此不受 Android 15「BOOT_COMPLETED 不能拉起 dataSync 前台服务」的限制。
* 兜底：`ServerService.onCreate` 里 `startForeground` 被拒时**主动 `stopSelf()` 优雅退出**，不让异常冒到 ActivityThread 造成开机崩溃循环（`START_STICKY` 会导致 AMS 反复重启，实测会连崩多次）。

#### 3.6.4 服务状态管理

* 右上角指示灯实时显示运行状态与当前模式。
* 省电模式由用户在上传页手动启动/停止（离开页面即停）。

## 4. 非功能性需求

### 4.1 性能

* 上传大文件（如 2GB MP4）时，App 内存占用保持在低水位（v1.30 起 multipart 手动流式解析：文件 part 以 **128KiB 缓冲边读边写**进临时文件，解析器堆占用 O(128KiB)，与文件大小无关；旧实现的 `FileChannel.map()` 内存映射对大文件会撑爆虚拟内存报 `Map failed` / `OutOfMemoryError`，已弃用）。
* 上传速度受局域网带宽限制，应尽可能接近满速。
* 媒体库**增量对账**（无新增 / 变更文件）1000 个文件 ≤5 秒；**首次全量入库**需为每个新视频提取时长（MediaMetadataRetriever，约 20~50ms/个），1000 个新视频约 10~50 秒，属一次性成本——期间媒体库随 Room Flow 逐条推送**逐步显示**，无需等待扫描结束（与 Kodi / Plex 首扫「先出列表、后补元数据」的主流做法一致）。

### 4.2 兼容性

* 支持 Android TV 5.0 (API 21) 及以上。
* 适配 Android 11+ 的分区存储（Scoped Storage）。
* 支持常见电视盒子芯片：ARMv7、ARMv8、x86。
* 手机网页兼容 Chrome、Safari、微信内置浏览器、Edge。
* **大屏自适应（v1.30）**：Android 16（API 36）起，最小宽度 ≥ 600dp 的屏幕会**忽略 `screenOrientation`**（平板 / 大折叠内屏 / 桌面窗口模式），且该行为将在 API 37 成为强制。本应用三个 Activity 均锁横屏，因此：清单声明 `PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` 作为**有保质期的安全网**，同时代码侧具备真正的宽度自适应 —— 顶部导航栏在宽度 < 960dp 时自动收窄（`TOP_BAR_FULL_WIDTH_DP`），`MainActivity` 补 `configChanges` 以免窗口变化重建丢状态。**手机（最小宽度 360~450dp）不受该变更影响；标准电视 / 盒子（≥960dp）逐像素不变。**

### 4.3 权限

* **存储权限**：申请 `MANAGE_EXTERNAL_STORAGE`（Android 11+ 需引导用户到系统设置手动授权）；Android 10 及以下走运行时 `WRITE_EXTERNAL_STORAGE` + `requestLegacyExternalStorage`。授权未通过时做**写探针**兜底（在沙盒 `/sdcard/TransView/Movies` 建删临时文件实测可写性）：部分模拟器/ROM 不强制分区存储但无授权入口，实测可写即放行；真实设备无授权时探测必然失败，行为不变。App 实际读写范围仅限专属沙盒 `/sdcard/TransView/`（见 §3.3.2），不触碰系统公共目录。这是本应用唯一的敏感权限，也是核心功能的唯一可行解（工程硬约束「禁用 SAF / DocumentFile，全程 `java.io.File`」）。⚠️ Google Play 对「所有文件访问」有政策申报要求；侧载分发不受影响。
* **网络权限**：`INTERNET`（局域网 HTTP 服务器 + Coil 缩略图）。`ACCESS_NETWORK_STATE` 由 `media3-common` / `media3-exoplayer` 声明（Coil 的 `RealNetworkObserver` 依赖它），本应用不重复声明；**`ACCESS_WIFI_STATE` 已删除**（v1.30：唯一使用者 `NetUtils.wifiManager()` 是死代码，且新系统上无定位权限时 SSID 恒为空占位值）。
* **前台服务权限**：`FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_DATA_SYNC`（API 29~33 回退）、`FOREGROUND_SERVICE_SPECIAL_USE`（API 34+ 主用）、`POST_NOTIFICATIONS`（**API 33+ 需运行时申请**：v1.30 起在存储授权通过后主动申请一次，见 `util/NotificationPermission`；拒绝不影响服务器运行，仅通知不可见）。
* **开机自启权限**：`RECEIVE_BOOT_COMPLETED`（设置页可开关，见 §3.6.3）。
* **明确未申请**：相机、定位、通讯录、电话、录音、蓝牙、健康数据、`AD_ID` —— 均与本应用功能无关，一个都没有。

### 4.4 稳定性

* 上传过程中断网，支持断点续传（P2 优先级）。
* 服务器连续运行 72 小时不崩溃。
* 异常捕获：文件写入失败、磁盘满、权限不足时，向手机返回明确错误信息。

### 4.5 安全性

* 局域网内传输，不加密（HTTP），但可考虑简单 Token 验证（可选）→ **已实现**：电视端 6 位访问码**会话内固定**（进程存活期内沿用，重启 App 才轮换），`/upload` 需带 `X-Upload-Token`、`/verify` 供预校验；扫码路径零输入无感，手输路径需照屏输入访问码（见 §3.2.6）。
* 上传页面不暴露电视文件系统路径。
* 防止路径穿越攻击（文件名过滤 `../` 等）。

## 6. 验收标准

1. 手机浏览器扫码后，能打开上传页面。
2. 选择“视频”分类，上传多个 MP4 文件，电视端“视频”页能看到文件（自动刷新），点击可播放。
3. 上传包含同名文件的文件夹，电视端自动合并文件夹，同名文件自动加序号。
4. 上传一部电视剧文件夹，电视端显示为文件夹，点击进入可看到剧集，播放第一集后自动播下一集（自然排序 EP2 < EP10）。
5. 视频播放到一半退出，再次打开提示续播，选择“继续”后从上次位置播放。
6. 上传图片到“图片”分类，电视端全屏展示，左右键切换。
7. 上传 APK 到“其他”分类，电视端调用系统安装器。
8. 服务器保活策略验证：极速模式下电视待机仍能上传；智能模式下待机/播放暂停、结束后自动恢复、15 分钟无上传休眠且可一键唤醒（<1 秒）；省电模式仅上传页手动启动。
9. 遥控器可流畅操作所有界面，无焦点丢失。
10. 上传进度在手机和电视端同步显示；上传完成后电视端列表自动刷新。
11. 沙盒存储验证：上传文件落盘在 `/sdcard/TransView/` 对应子目录；U 盘拷入 `/sdcard/TransView/Movies/` 的电影经对账刷新后出现在媒体库；系统公共目录（`/sdcard/Movies/` 等）中的文件**不会**被扫描展示。
